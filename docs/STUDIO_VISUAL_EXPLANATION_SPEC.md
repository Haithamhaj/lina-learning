## A. Product behavior and routing

### A1. Approved behavior

Studio is a living reusable learning Workspace across subjects, not four lessons or four services. The approved V1 patterns are `process_cycle`, `labeled_diagram`, `geometry_scene`, and the single quantity/fraction family `fraction_model / quantity_visual`. Chat/Tutor remains the only Student-facing teaching authority. The same primary Tutor call decides whether a visual helps the current request. Chat-only is a successful outcome when it does not.

Books improve grounding and priorities; no book, no retrieval match, or incomplete curriculum semantics must not prohibit explanation. Current Student behavior outranks historical personalization. These responsibilities live inside the existing modular monolith, not new Visual Planner, Router, memory, RAG, or scene-store services.

### A2. End-to-end flow

1. The existing context builder supplies the current request/exchange, Segment context, relevant intelligence, Personal Memory as its separate existing input, current Studio state/unseen Events, capability guidance, and optional authorized retrieval sources. Add only a compact eligible instructional-content list through the existing Workspace capability context (C2).
2. The primary Tutor returns normal teaching text plus nullable educational WorkspaceIntent. For a supported pattern it may additionally return one bounded content proposal, eligible content reference, or state update. It never chooses a renderer library or writes state.
3. The existing deterministic Router validates capability and request compatibility. Preserve a suitable active Scene; otherwise honor source/annotation needs when an implemented capability exists; otherwise select an exact known visual/interactive pattern. Resolve an eligible reusable content version or validate the proposed new content. A new example in a known pattern is still `KNOWN_VISUAL`/`KNOWN_INTERACTIVE`, not `CUSTOM_COMPOSE`.
4. The existing activation bridge checks persisted Tutor-message/execution lineage, current turn, Student/session ownership, policy, source permission, and exact contracts. It accepts and activates through Studio state authorities. It does not report a visible Canvas until committed state is available.
5. The existing resumable Studio feed delivers committed Scene/Snapshot state to the existing Renderer Host. Application code owns rendering, layout and interaction. Tutor SSE continues to own Chat, with its persistence-before-terminal behavior.
6. Meaningful semantic interactions use registered actions, existing command admission, reducers, Events and Runtime-03 StudentInteraction. The same Tutor receives selected state and unseen Events. No drag causes a default model call; no fake Student message is synthesized.
7. Reload reconstructs the Student's attempt. Eligible reuse seeds a distinct Student-owned instance from immutable instructional content. Updating shared content never rewrites an earlier attempt.

Admission sequence (proposed implementation boundary):

1. Apply existing pre-generation Safety behavior, then receive the primary result through the Gateway. Provider strict-schema enforcement constrains representable fields/types; it neither proves completion nor checks scientific meaning. A provider refusal or failure may yield no contract-shaped answer.
2. Confirm successful completion and parse the whole required v10 envelope, including the present-but-nullable sibling and schema-valid union body; independently validate normal Tutor fields and apply existing effective Safety/Parent Boundary handling. Missing/invalid required fields or incomplete output follow the applicable existing Tutor failure/refusal path. Do not salvage arbitrary prose or coerce a missing sibling to null.
3. Only after a complete, schema-valid response and usable policy-permitted Tutor result exist, perform application visual admission: intent/body consistency, semantic references/relations, domain constraints, capability/mode, permissions, content checks, asset availability and captured Scene version. This is the boundary at which a schema-valid but inadmissible visual can be rejected independently. A failure in the nested strict schema itself belongs to step 2, not visual-only recovery.
4. Retain validated Tutor text through its existing persistence/terminal lifecycle. Persist Tutor lineage before activation, then accept the visual through existing Studio authorities with an all-or-nothing visual write boundary. Implementation must ensure a failed visual write does not leave a failed database transaction or partial Scene replacement that invalidates otherwise usable Chat. An unrecoverable whole transaction failure uses existing Tutor error behavior, not a promised successful turn.
5. Render only committed accepted Scene state. Recheck asset access when serving; retain an old Scene only where it is still permitted by current policy. A visual refusal must not leave contradictory claims such as “the diagram is now visible”: the primary response must avoid asserting display before commit, and the application supplies truthful availability/fallback status.

| Failure/choice | Applicable behavior |
|---|---|
| Explicit `workspace_scene_proposal: null` in a valid response | Normal Chat; no new visual mutation. Existing permitted Scene may remain under NO_CHANGE |
| Complete schema-valid Tutor result, but visual relations/domain/intent checks fail | Reject visual only; keep usable policy-permitted Chat and checked text fallback; no partial Scene replacement |
| Asset denial, missing asset or load failure | Omit denied content and use a permitted semantic/static/text equivalent; do not disclose protected source details or promise a recovered image |
| Missing/invalid required v10 field (including sibling/body schema), incomplete response or provider failure | Existing applicable Tutor error/retry behavior; no guaranteed usable Chat and no implicit null |
| Safety refusal or effective policy redirect | Existing applicable refusal/redirect/enforcement behavior for Tutor and visual content; no recovery that bypasses policy |

A source-view/annotation routing decision does not prove that a source/annotation renderer exists today. No failure activates the specialist automatically. B1 defines the strict-contract boundary; D3 compares the resulting failure tradeoff.

## B. Four-pattern contract and integration

### B1. Proposed bounded output contract

Keep `WorkspaceIntent` v1 intact. In proposed Tutor output v10 add `workspace_scene_proposal: null | WorkspaceSceneProposalV1`. The new sibling is associated with the same persisted Tutor turn and consumed only by Studio. This makes the extension explicit without widening existing educational text fields. The primary call is allowed to describe content, not implementation. No proposal may contain Student IDs, storage paths, renderer keys, callbacks, formulas-as-code, HTML, arbitrary SVG paths, remote URLs or JavaScript.

`WorkspaceSceneProposalV1` has `version: "workspace-scene-proposal-v1"` and a strict discriminated union (unknown properties rejected):

| Variant | Allowed data | Server interpretation |
|---|---|---|
| `REUSE` | Opaque candidate handle supplied in the current capability context; exact content version; objective compatibility assertion | Resolve handle within current Student permissions; recheck full compatibility. No inferred reuse by title and no model-supplied permission/review status |
| `CREATE` | `pattern`, `pattern_version`, `mode`, plain objective, locale/direction, bounded concept keys, source handles, plain text equivalent, one typed pattern body | Validate body, derive canonical metadata/hash, assign private content identity/version and seed a Scene. `quantity_visual` is canonical; `fraction_model` is its fraction mode, not a fifth renderer |
| `UPDATE` | Current Scene context handle, captured base version, 1–6 typed operations over existing object handles | Resolve server-owned Scene identity, reject stale/mismatched versions; atomically append registered semantic operations. No arbitrary JSON Patch, structural object insertion or code execution |

Proposed CREATE bounds: one pattern per turn, up to 12 objects, 20 relations, 6 source refs, 2 optional asset handles; labels ≤120 characters, each explanation ≤300, text equivalent ≤1,200; whole canonical content body ≤8 KiB UTF-8. Both cardinality and total-byte limits apply, including Arabic bytes. IDs are opaque, locally unique handles ≤64 characters, never answer encodings. `mode` is `EXPLAIN`, `EXPLORE`, or `GUIDED`; only the exact mode advertised by a registered capability is eligible. A proposal cannot enable a guided mode or grading policy by declaring it.

Body → persisted seed expansion must fit existing 16,384-byte scene and snapshot budgets; Events fit 8,192 bytes and current interaction payloads 4,096 bytes. Check the final serialized envelopes, not just the body. Do not raise global limits to accommodate verbose generation. Strict provider-schema and runtime-schema parity is a release gate. Invalid schema fields or missing v10 siblings are whole-contract errors; `null` is an explicit valid choice and is never synthesized from absence. Final byte-capacity, cross-field consistency and semantic/domain checks performed after successful strict parsing can reject only the visual when the normal Tutor response is independently valid and policy-permitted (A2). A provider-side schema rejection or incomplete envelope cannot be treated as a recoverable visual-only error. Keep strict parsing separate from post-parse visual admission rather than weakening the output schema to obtain fallback.

CREATE requires compatible `OPEN_ACTIVITY` and `VISUAL`/`INTERACTIVE`; UPDATE requires `UPDATE_ACTIVITY` and a current supported Scene. REUSE may preserve the current eligible Scene or create a distinct attempt when opening content for a new session/request. Null/NO_CHANGE never activates a proposal. Pattern and mode must agree with the educational intent and Registry. Proposal source handles must be in the authorized context. The application derives real IDs, profile/renderer versions, permission scope, review state and provenance; the model cannot certify those fields.

Updates initially allow `SET_HIGHLIGHT(object_ids)`, `SET_REVEALED(object_ids)`, and `SET_PARAMETER(parameter_handle, bounded_value)`. Parameters are declared by the accepted seed and exact domain contract. They do not authorize relabeling scientific facts or changing source/whole/objective silently. A changed instructional body requires a new immutable content version and a new Scene; ordinary highlights, reveals and permitted parameters retain the Scene and history. Persist original content plus operations so follow-ups and replay never depend on regenerating model output.

### B2. Shared interaction and validation semantics

These are proposed registered action names, not claims that they exist now. Each registration supplies an exact event kind/payload version, payload validator, reducer, actor restriction and interaction policy using existing `ActivityActionContract` machinery. Use a `visual-explanation-v1` event/payload namespace; retain Core lifecycle `studio.scene.accepted`, `studio.scene.activated`, and `studio.scene.status_changed`.

| Semantic action | Event/state effect and Tutor semantics |
|---|---|
| `SELECT_OBJECT`, `REVEAL_OBJECT`, `SET_HIGHLIGHT` | Record bounded object IDs/reveal/highlight state; `RECORD_ONLY`. Keyboard focus, hover and raw pointer coordinates are transient and not learning events |
| `MOVE_CONSTRAINED_POINT`, `SET_QUANTITY`, `SELECT_RELATION`, `ASSIGN_LABEL` | Only when exact pattern/mode advertises it. Commit semantic end state after structural/domain checks; `RECORD_ONLY`, not per-frame events. Label assignment selects supplied opaque labels; no free text |
| `REQUEST_EXPLANATION` | Selected object/relation IDs and current configuration only; `TUTOR_TRIGGERING`, one existing Runtime-03 continuation. No deterministic correctness verdict is implied |
| `SUBMIT_CONFIGURATION` | `TUTOR_TRIGGERING` only for an enabled guided activity with a versioned server validator; preserve submitted configuration and its result separately from later exploration |
| Tutor-originated UPDATE | Application maps validated operations to registered Tutor-only events. `RECORD_ONLY`; must not create a StudentInteraction, count as Student performance or recursively call Tutor |

For non-graded exploration, `SemanticValidationPolicy.NONE` means no academic answer grading for that action. Payload, safety, ownership, content admission, permitted parameter ranges and geometric/quantity invariants still apply. Guided/graded modes require `SemanticValidationPolicy.REQUIRED` and exact server validator key/version. Reuse existing `VALID`, `INVALID`, `UNDER_SPECIFIED`, `VALID_ALTERNATIVE`, `INCOMPLETE`; never reinterpret `VALID` as scientific certification or mastery. Help/explanation may reach the Tutor without an answer key; a correctness badge may not.

Cross-actor restrictions for the new actions require explicit enforcement at admission: a Student cannot submit a Tutor-only highlight/update command by changing an actor field. Record-only events remain observable under the existing watermark; Tutor-triggering events preserve current exclusive claim, cancellation, causal ordering and immutable submitted-state lineage. Rejected operations do not become accepted Events. No direct Candidate, Evidence, Personal Facts or intelligence writes.

For review, proposed durable event kinds map one-to-one to these actions: `visual.object.selected`, `visual.object.revealed`, `visual.highlight.set`, `visual.point.moved`, `visual.quantity.set`, `visual.relation.selected`, `visual.label.assigned`, `visual.explanation.requested`, and `visual.configuration.submitted`. Tutor `SET_PARAMETER` maps to `visual.parameter.set`; Tutor reveal/highlight use the same semantic kinds with server-assigned Tutor actor. Every registration pins `visual-explanation-v1` event schema plus its exact action-payload schema. These names extend subject action registrations; they do not add a new feed or change Core event sequencing.

### B3. `process_cycle` — process and relationship explanation

- **Purpose:** Explain a finite process, recurrence or supported branching relationship. Unsuitable for unrestricted concept maps, continuous physical simulation or implying a single order where the source supports alternatives/parallel paths.
- **Semantic body:** 2–12 labeled stages/entities, up to 20 typed directed relations (`precedes`, `transforms_to`, `returns_to`, `branches_to`), optional branch condition/caption and source handles per relation. Topology declares `sequence`, `cycle`, or `branched`; it controls layout without fabricating links. A cycle requires an explicit supported return relation. Do not close an arrow because the pattern is named process_cycle.
- **First-slice modes/actions:** Bounded EXPLAIN sequences and cycles, including an explicit source-supported return relation, are in slice 1. Selecting an object, highlighting/de-emphasizing, revealing it, and requesting an object-specific Tutor explanation are explanatory controls; selection/highlight/reveal are record-only and an explicit explanation request triggers Runtime-03. Advertise only these exact supported actions; their presence does not enable graded ordering or graph editing. The renderer contract must accurately advertise its control support even though the instructional mode is EXPLAIN.
- **Later modes/actions:** Multi-branch/merge, conditional/parallel paths and arbitrary graph topology remain later process work; they are not required for the first sequence/cycle slice. Node creation/deletion, rewiring and unrestricted graph editing remain outside bounded V1 and need separate demonstrated need/approval. Guided order/relation grading waits for slice 4 and a source-reviewed server rule with allowed alternatives. The accepted sand/water filtration ordering activity remains its existing precise activity; it is not the new first-slice deliverable.
- **Checks/limits:** Unique IDs, resolvable endpoints, no duplicate edges or undeclared self-loops; declared topology consistency and bounded captions. A graph check cannot establish causality, timing, conservation or scientific truth. Each instructional claim/arrow must be supported by the selected source or explicitly identified as a model-knowledge draft. Never grade from a model-invented answer key.
- **Fallback:** Ordered or grouped text lists with explicit named relationships, branch conditions and return explanation; keyboard list selections equal pointer selections. Narrow layout may use stacked stages plus relationship text without changing topology.
- **Reusable examples:** Water movement between surface, atmosphere and ground (include only grounded paths, not a forced ring); a sourced butterfly life cycle; source-supported filtration steps; language writing/revision (`plan → draft → review`, with revision returning to draft only when taught). The language example uses the same body/parser/view and ENGLISH or ARABIC subject registration, not Science attribution because arrows exist. These are design cases, not newly verified instructional sources or prepared lessons proving generation.

### B4. `labeled_diagram` — parts and relationships

- **Purpose:** Identify parts, positions and function in a coherent whole. Unsuitable when numerical geometry must be exact, a photo is ambiguous, or a label would pretend to identify an uncertain biological structure.
- **Semantic body:** One application-owned schematic type or authorized referenced image; up to 12 parts/labels with normalized anchor regions, optional `part_of`/`connected_to` relations, reveal group, and source handle. No arbitrary drawing markup. Image-relative anchors refer to a specific immutable image version and aspect ratio; reject out-of-bounds regions. Schematic types are bounded rendering shapes, not lesson IDs.
- **Modes/actions:** EXPLAIN shows/reveals labels; EXPLORE selects a part and requests an explanation. GUIDED permits assignment of supplied labels to defined parts followed by submission against a server-reviewed answer mapping, including declared alternatives. Labels that reveal the answer must not masquerade as an independent assessment.
- **Checks/limits:** Existing part references, bounded geometry, complete text equivalent; source/asset match, meaningful labeling and visibility review. Normalized coordinates alone do not prove that an arrow points to the correct part. A generated image cannot supply anatomical truth. If useful illustration is unavailable, use an honest text explanation rather than a confusing collection of boxes.
- **Fallback/examples:** Accessible part-name/function list and label-assignment controls. A plant's parts, a simple circuit's components, and subject/verb/object spans in a short English or Arabic sentence use the same labeling pattern. Language spans reference grapheme-safe text ranges/opaque tokens in the immutable content, retain diacritics, and do not add a general grammar grader or replace accepted sentence-ordering activities.

### B5. `geometry_scene` — explanation versus constrained manipulation

- **Purpose:** Explain geometric relationships, measurements and invariants. Distinguish a labeled illustrative drawing from a mathematically constrained construction. Unsuitable for arbitrary theorem proving, unrestricted construction tools, 3D, or treating a sketch/pixel distance as a measurement.
- **Semantic body:** Up to 12 points, segments, circles, polygons and angle markers counted within the shared object cap. Exact scalar data uses bounded rational pairs; relations are allowlisted `incident`, `parallel`, `perpendicular`, `equal_length`, `fixed_distance`. Each constrained point has a declared domain and application-owned construction rule. No expressions, scripts or JessieCode from the model.
- **EXPLAIN:** Application lays out a labeled shape. An illustrative not-to-scale view states this; exact values/claims must agree or be omitted. Highlight side/angle/height without reconstructing the Scene.
- **EXPLORE/GUIDED:** Move only enabled points using pointer or coordinate/step controls. The renderer projects motion onto the allowed domain; the server recomputes and validates the submitted canonical configuration with a declared tolerance/rounding policy owned by the exact domain contract. GUIDED submission requires an application-owned criterion, never a browser/library assertion of correctness.
- **Stress case:** Drag the top of a triangle along a line parallel to its fixed base; the application maintains a fixed perpendicular height and computes area from the accepted base/height. This is different from explaining labeled triangle parts. Degenerate/self-intersecting constructions, incompatible constraints or out-of-domain moves are rejected without changing accepted state. Exact rational invariants use exact arithmetic; approximate constructions must explicitly declare numeric limits and tolerance before promotion.
- **Fallback/examples:** List points, relationships and measurements with equivalent keyboard controls; a rectangle's perimeter, triangle base/height/area, and circle radius/diameter use the same geometry view with different semantic bodies. A visual triangle-angle sum is not proof of a general theorem. Dynamic geometry library output is never server validation authority.

### B6. `fraction_model / quantity_visual` — explicit wholes and values

- **Purpose:** Show quantities, equal parts, equivalence and comparisons. Unsuitable for fraction algorithms, decimal operations, measurement accuracy, division strategy or ratio claims beyond the enabled mode. Approved family direction does not authorize full fraction arithmetic.
- **Semantic body:** Canonical pattern `quantity_visual`, `representation` of `equal_parts_bar`, `equal_parts_area`, or `discrete_set`; stable whole IDs, unit, exact rational whole value, equal partition count, selected part IDs and optional explicit mapping between equivalent representations. Proposed initial denominator cap 12 and total visible parts/items 24 (body's semantic object cap counts whole/model objects, not repeated generated partition marks). No floating-point source truth.
- **Modes/actions:** EXPLAIN shows unit fraction/simple equivalence; EXPLORE changes the number of selected parts or an allowed partition parameter and highlights equivalence. `SET_QUANTITY` is record-only; GUIDED submission needs exact server arithmetic and whole/partition validation. No arbitrary field entry or model-authored grading rule.
- **Invariants:** Whole identity and unit remain explicit; denominator positive; each partition is equal measure within its whole; selected membership unique and within range; selected value = whole value × selected count / partition count. Equivalent forms require equal total value and compatible whole/unit, not equal shaded area on differently scaled pictures. Improper fractions need explicitly multiple equal wholes; exclude them from the initial simple-fraction mode. Changing a denominator cannot silently preserve an incompatible selection or change the whole; revalidate the entire state.
- **Fallback/examples:** Text such as “3 of 4 equal parts of one whole; value 3/4”, with increment/decrement controls. Three quarters of a strip, half of a declared set of 8 counters, and two fourths compared with one half reuse the same family. A Science quantity example may show parts of an explicitly defined sample; do not infer a measurement from the picture.
- **Non-duplication:** Keep accepted Make-Ten transfer, decimal number-line comparison/rounding, and exact hundredths place-value ADD/SUBTRACT on their existing contracts. Route compatible precise tasks there. Fraction operations, fraction number-line modes and division retain the corrected renderer planning scope and separate promotion; this family does not claim their coverage.

## C. Generation, persistence, reuse, and privacy

### C1. Three identities and smallest storage extension

| Entity | Authority and lifetime |
|---|---|
| Pattern/template | Application-owned versioned schema, view/layout policy, actions and validators registered through Subject Capability. Reusable without containing any Student information; no new template platform |
| Instructional content version + optional assets | Immutable semantic content, provenance, selection metadata and rights. Can be reused only within permission scope and after compatible selection; not an attempt |
| Student Scene instance + Events/Snapshot | Existing `StudioScene` with its seed, exact contracts, source Tutor lineage and Student/session ownership; Events preserve interaction history, Snapshot is rebuildable. Existing `status = ACCEPTED` means accepted into Studio state, not academically reviewed or Product Owner accepted |

Current `StudioScene` is explicitly Student/session-bound; `ContentDocument` ingestion accepts PDF/Markdown originals and deduplicates per Student checksum. Neither is a global reusable scene library. Do not overload a Student Scene as shared content or a generated description as an original book.

Propose one immutable PostgreSQL relation, provisionally `StudioInstructionalContentVersion`, inside existing Studio persistence: content ID/version, pattern/contract version, typed body JSONB/hash, objective and parameter signature, subject/concepts, locale/direction, supported level range, source refs/revisions, asset manifest, scope/owner, rights/review metadata and creation lineage. Default scope `STUDENT_PRIVATE` with owner required; only authorized project-reviewed records may have `PROJECT_SHARED`. Rights scope is the intersection of all sources/assets, never broader than an underlying source. An immutable superseding record carries review/rights changes; revoked items are excluded from new selection.

This additive relation is proposed because content needs independent immutable identity, permissions and indexed selection without copying attempts. It is not another scene store: no Student answers, mutable positions, Event log or Snapshot belongs there. Use existing PostgreSQL transactions/indexes, not vector infrastructure or a new service. Store a pinned content reference/hash and full safe semantic seed in existing Scene JSONB, avoiding a required new Scene column in the first slice. Validate references in the activation transaction. Keep protected server grading criteria out of browser seed/feed payloads; a content variant with assessment uses a private versioned validator policy reference.

Generated content may inadvertently echo Personal Memory or Student details even when prompted otherwise. Therefore every new model-generated record starts Student-private and unreviewed, independent of whether it looks generic. There is no automatic cross-Student promotion or automated “anonymization” promise. A shared version must be separately authored/reviewed from instructional sources, with positive checks that it contains no names, Personal Facts, answers, original Student work or interaction logs. A saved Scene never becomes a shared record by copying it.

### C2. Selection and reuse without another semantic pipeline

Use ordinary permission/metadata queries in the existing application database. Before the primary call, the Workspace capability context may expose up to six permitted candidates with objective, pattern, parameters, subject/concepts, level, locale, source/version, review status and opaque handles. Each candidate must also include a bounded semantic representation sufficient to describe what selecting it will show: relevant object IDs and labels, instructional captions/values, directed relations including return/branch conditions, whole/unit or geometry constraints where relevant, initial reveal/highlight state, permitted actions and their targets, and asset meaning/semantic anchors when the explanation depends on them. This is structured content from the pinned version, not a title-only search result or a model-generated summary. Never include private answer keys. Prioritize active content, eligible Student-private content and approved shared content within the existing metadata selection; authorized retrieval source IDs may narrow candidates. Metadata supplies candidates, not a semantic verdict; no regex classifier, extra call or embedding pipeline is added.

Reduce candidate count (including to one or zero) when the final existing context budget cannot hold the essential meaning of each candidate; do not silently truncate an essential label, relation, constraint or action. Preserve protected current request/immediate exchange and existing capacity rules; never inject the whole library. A candidate whose relevant meaning cannot fit is not selectable in that turn. The primary Tutor compares this pre-call content with the current objective, describes only the scene it has actually been shown semantically, and returns REUSE or CREATE in the same call. The server enforces exact versions, mode, numbers/units/whole, locale/level, sources and permission; the Tutor owns semantic objective compatibility. Uncertainty declines reuse. A post-call lookup must not substitute unseen instructional content or a newer version. If a candidate was not supplied before response generation, it cannot be claimed as pre-call reuse. An exact-body hash may deduplicate a newly generated body within the same provenance/permission scope afterward; log that as CREATE with post-call deduplication, not REUSE and not proof of avoided generation.

Open reused content in a new Student-owned Scene with a fresh initial state and no borrowed answers/history. Resume of the same saved Scene is a distinct action from opening a new attempt. Cache keys include content/version/hash, pattern and payload versions, objective/parameter signature, mode, source revision, locale/level and permission scope. Never serve a private cache entry based on another Student's key or expose cross-Student hit metadata.

Historical seed, renderer/reducer versions and Events remain pinned. Template updates affect future instances only. Exact unavailable historical contracts must give an honest accessible fallback, not silently use the newest renderer. Preserve immutable bytes for reproducibility while enforcing current access/revocation restrictions: historical reproducibility does not permit serving a revoked asset. Show retained semantic text where permitted and a clear unavailable-media state.

### C3. Content admission and factual authority

Separate `STRUCTURE_CHECKED`, `SOURCE_LINKED`, and `REVIEWED` concepts; never collapse them into “correct”. The model can propose source handles and claims; the server can verify existence/ownership, exact arithmetic and declared constraints, but cannot prove scientific entailment by checking IDs. A human/domain review must inspect important claims, arrows, omissions and labels against the cited source during acceptance. Source material is untrusted grounding data, never instructions overriding policy.

General educational knowledge remains allowed with provenance `MODEL_KNOWLEDGE` and private `UNREVIEWED` status. Do not invent citations. Source-sensitive uncertainty should produce a simpler qualified explanation or Chat clarification, not confident invented relations. Unreviewed content never becomes a graded answer authority or shared reviewed item. Admission applies the existing effective Safety/Parent Boundary decision to all visible labels, captions, equivalent text and media, including reused content; reuse cannot bypass changed policy. Runtime implementation must suppress restricted visual output together with the restricted Tutor answer. Prompt-only safety is insufficient.

Generated and reused visual text enters normal Tutor/interaction history only through existing boundaries. Selecting, displaying, liking or repeating a Scene is not proof of learning. Existing Segment review and Session-authorized Evidence/intelligence remain authoritative; this task changes neither Personal Facts extraction nor learning measurement.

1. **Inspect:** inspect appearance and source markup, instructional correctness, license and active content (scripts, event handlers, embedded foreign content or remote references). Reject unsafe/unclear sources or prepare a reviewed safe derivative; conversion alone is not admission.
2. **Retain source/provenance:** preserve original bytes, source/license record and checksum; create a separate derivative rather than overwriting the original.

6. **Register:** approve the exact asset version/manifest within existing application assets/content metadata and permission checks. No new asset-management service or runtime importer is implied.

Authorization resolves opaque handles; key syntax does not confer permission. Asset access failure uses A2's permitted fallback; do not imply the whole Tutor result is recoverable when its contract failed. No artwork download, conversion, optimization or registration is performed in this documentation revision.

Generated images remain optional/deferred. Any future authorized image task must use Model Gateway with an explicit provider-neutral capability/asset-result contract, task-level model routing, usage/cost/failure lineage, privacy/retention and rights review, and a bounded deadline. ## D. Visual quality, correctness, and focused library comparison

### D1. Visual acceptance contract

Use the accepted warm, coherent Daily Student visual system for roughly ages 10–18. Retain the existing shell and shadcn/local controls. ### D4. Small application-owned motion vocabulary

Motion for React is the preferred first animation candidate under D2's approval boundary. These are production constraints and five reusable recipes, not a frozen detailed animation API or another runtime agent. The model selects semantic targets/allowed actions already declared by the pattern/asset; application code chooses implementation, easing, bounded durations and layout. No model timelines, formulas, scripts or raw path strings.

| Recipe | Educational purpose and meaning-preserving rule | Static/reduced-motion equivalent |
|---|---|---|
| Highlight / de-emphasize | Emphasize selected part/relation while retaining readable context; never encode correctness solely by color | Stable outline/contrast plus named selected state; keep context labels readable |
| Progressive reveal | Introduce existing stages/labels in instructional order; do not invent a dependency by appearance order | Immediate selected reveal state or explicit next-step control; accessible reading order |
| Trace existing relation/path | Draw attention to an application-owned existing arrow/path in its declared direction; not a new causal claim | Complete highlighted relation with visible arrowhead and relationship text |
| Move along declared instructional path | Follow a reviewed semantic path/asset handle only; decorative travel must not imply measured speed, actual chronology or unsupported causality | Start/end markers and a concise movement description; no animated travel |
| Equivalent grouping/partition transition | Show two valid representations of the same explicit whole/value using declared correspondence; never imply quantity creation/loss or unequal parts as equal | Side-by-side or stepped valid representations with unchanged whole/unit/value labels |

First-slice process views use highlight/de-emphasize and progressive reveal; trace/move are optional only where a reviewed relation/path makes the explanation clearer. Grouping/partition transitions belong with the quantity slice and its exact invariants. No recipe is required merely for decoration. Trusted artwork can provide complex paths once at development time; runtime requests reference semantic handles.

Persist accepted semantic end states using the existing Studio action/Event rules, not animation progress. Transient frames, hover and unfinished motion never create database Events or model calls. A view transition depicts an already accepted target; drag previews and unaccepted changes remain provisional and reconcile on rejection. Interrupt/cancel playback by settling to the latest authoritative state, without emitting completion evidence. On supersession, stop old motion immediately and render the newer Scene/version; late callbacks cannot mutate old state. Reload displays the accepted end state without replaying old animation as a new interaction. Unmount cleans up playback/listeners; controls remain usable during transitions.

Application recipes set finite timing/easing bounds during implementation and avoid indefinite loops. Reduced motion uses the static equivalents above and removes spatial travel; pause/skip controls apply when playback is lengthy enough to need them. Labels and key values remain legible and anchored at initial, intermediate and final states; arrows must retain direction, geometry must retain constraints, and quantity must remain conserved. Intermediate interpolation is presentation, not a new mathematical/scientific state or measurement. If an honest transition is unavailable, switch directly or use labeled before/after views.
