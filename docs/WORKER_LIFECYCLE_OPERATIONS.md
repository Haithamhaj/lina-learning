The current worker remains the sole executor of existing jobs and handlers. The existing `lina-app` FastAPI process acts as an external lifecycle controller. A Cloud Scheduler HTTP job calls its authenticated `/api/v1/internal/worker-lifecycle/tick` endpoint every minute, including while the worker pool has zero instances. Authenticated session start/resume, Student turns, voice transcription, non-replayed Studio operations, and admitted Canvas interactions record a global activity timestamp. The first wake request runs synchronously before the HTTP response ends; while the pool is already on or starting, later messages only update the shared activity clock and use a PostgreSQL state check, with no Cloud Run Admin API call. Browser polling, an open tab, and Canvas status reads do not refresh activity.

The Worker Pool has no inbound URL or request-driven autoscaling, so a database job cannot restart it at zero. A timer inside the worker would also stop at zero. Reusing the app plus one Scheduler job is smaller than adding an autoscaler service, Cloud Tasks, Pub/Sub, or a second queue. Cloud Run manual scaling explicitly supports an external controller and does not guarantee an idle retention period.

The controller checks one global 20-minute window since the **last** genuine action by either user, immediately runnable **supported** jobs, and all RUNNING jobs. It scales the **existing** Cloud Run Worker Pool between zero and one instance through the Admin API. Unsupported PENDING historical rows cannot pin the pool on; investigate them separately. An unknown RUNNING row blocks shutdown because it may belong to an overlapping prior revision and needs operator investigation. The controller also runs the existing 20-minute inactivity plus 5-minute grace session-closure function on every tick; it queues the same idempotent finalization and Learning Intelligence work. Delayed jobs and retries wake on the first tick after `run_after`. No new queue, worker handler, or model route is introduced.

## Operational behavior and monitoring

- A synchronous wake attempt avoids reliance on Cloud Run CPU after the response. If the request or Admin API fails, the minute tick reads durable activity and jobs and recovers. A stop operation already in progress must finish before the next start; the first Canvas can still wait for the next successful tick plus Cloud Run startup and queue polling. Measure this, rather than promising instant startup.
- The controller serializes scaling through one PostgreSQL row. The worker locks that row before claiming a job. Shutdown holds the gate, rechecks activity/jobs, and requests zero only if both remain idle. Activity or jobs committed during the Admin API call are rechecked and trigger a subsequent scale-up after the zero operation completes. A missed signal is recovered by the next tick.
- Watch Scheduler last execution and 4xx/5xx counts; app `Scheduled worker lifecycle tick` and wake-failure logs; Cloud Run operation errors and `terminalCondition`; worker startup/restarts; unsupported due queue rows; runnable queue age; failed lease renewals; and session finalization/Intelligence lag. Alert on a missed tick, a failed pool condition, or a due supported job that remains unclaimed after the measured cold-start allowance.
- A running handler renews its five-minute lease every 30 seconds, and a Canvas handler checks its lease token before provider preflight. Agentic Canvas now stops a cooperative async provider attempt at its existing five-minute admission deadline; the deadline has **not** been extended. Cancellation does not guarantee reversal of an in-flight provider charge or a blocking tool subprocess. A worker crash or DB partition can still cause at-least-once retry and a duplicate external call; lease tokens fence queue settlement, not provider billing. Keep maximum pool count at one, measure handler durations and restart overlap, and do not claim exactly-once execution.
- The app and the database continue running; this changes only the Worker Pool count. The scheduler must stay enabled for delayed jobs and session finalization while all users are away.

## Rollback

Pause the Scheduler job and disable app lifecycle reconciliation first. Wait for any in-flight worker-pool operation to finish. Set `worker_lifecycle_state.stop_requested=false` and manually set the existing pool to one instance. Verify a due synthetic job is claimed and session finalization runs. Deploy previous app/worker immutable images or leave the new code disabled; the additive migration may remain. Do not set the pool to zero during rollback. Remove the dedicated Scheduler job/identity only after service is stable; there is no new app scaling grant to revoke.

The bounded rollback commands are `gcloud scheduler jobs pause lina-worker-lifecycle-tick --location=europe-west1 --project=project-lina-2016`, `gcloud run services update lina-app --update-env-vars=WORKER_LIFECYCLE_ENABLED=false --region=europe-west1 --project=project-lina-2016`, and `gcloud beta run worker-pools update lina-worker --instances=1 --update-env-vars=WORKER_LIFECYCLE_ENABLED=false --region=europe-west1 --project=project-lina-2016`. Keep the migration tables; their presence does not change old code behavior. Restore the pre-change image digests above only if the new revision itself is unhealthy.

## Cost and limits to review

One worker instance is billed through the 20-minute trailing window from the last genuine activity, all running job time, and startup/shutdown time. Zero-instance periods avoid worker instance charges. One Cloud Scheduler job is billed by **job count**, not per minute execution; the billing account's first three jobs are currently free, then $0.10 per job per 31 days. The minute tick also adds app requests, PostgreSQL queries, and Cloud Run Admin API reads; actual totals depend on existing billing, resource size, user cadence, and cloud startup duration. Measure before/after billable worker-instance time rather than quoting a guaranteed saving.
