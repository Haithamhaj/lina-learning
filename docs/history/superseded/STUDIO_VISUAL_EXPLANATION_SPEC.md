### A2. End-to-end flow and asynchronous admission

The primary Tutor remains the sole Student-facing teacher. Keep three independent routing facts: **representation/execution mode** (`KNOWN_VISUAL`, `KNOWN_INTERACTIVE`, source/annotation or separately bounded `CUSTOM_COMPOSE`); **content origin** (authored, reused, newly composed); and **requires specialist execution** (yes/no). An unseen example inside a registered process pattern is known-mode content requiring composition, not automatically CUSTOM_COMPOSE. Books remain optional grounding.

| Request | Primary Tutor / Studio responsibility | Composition calls |
|---|---|---|
| Chat-only | Normal teaching; null visual order | 0 |
| Exact activity or compatible reusable content | Select existing capability/content after informed pre-call evaluation (C2); Studio rechecks eligibility | 0 |
| Supported highlight/reveal/parameter change | Bounded UPDATE through current Studio admission/actions | 0 |
| New content or substantial recomposition within a registered pattern | Compact COMPOSE order; Studio admits one logical job; Worker/Gateway specialist returns one typed scene proposal | Normally 1 additional Canvas call |
| Object-specific explanation of an accepted Scene | Existing Runtime-03 Tutor with actual Scene context; no fabricated Student message | 0 unless a distinct subsequent composition need is explicitly admitted |
| Broader custom composition | Existing separately bounded CUSTOM_COMPOSE eligibility, not blanket pattern/platform permission | Not activated by this design |

**Admission sequence:**

1. Existing Safety/context and C2 informed candidate selection feed the primary Tutor. The proposed required-nullable visual order accompanies normal Tutor output. No specialist dispatch from provisional prose, partial streaming JSON or a speculative intent. Provider strict schema checks shape, not scientific truth; validate completion, the whole required primary envelope and normal Tutor fields, then enforce the applicable Safety/Parent Boundary decision. Missing/invalid required fields are never converted to null.
2. Post-parse application admission checks the order/control against the objective, enabled capability/mode, source/asset permissions, limits and current causal state. Reject a semantically invalid visual order without mutating a Scene when normal Tutor output is independently valid and permitted. Persist accepted Tutor lineage and the admitted order using the existing message/operation boundary. A required whole transaction failure follows existing Tutor behavior; no guarantee of salvaged Chat.
3. For COMPOSE, atomically enqueue one idempotent Job and link one pending CanvasSpecialistRun with the accepted order/lineage, in the existing persistence transaction after Tutor lineage is persisted and before commit. Queue visibility after commit is the durable scheduling boundary; the Worker cannot claim uncommitted rows. This transactional admission avoids a commit-to-in-memory-dispatch loss window. If optional queue/run admission fails, roll back that whole optional admission unit and preserve usable Tutor persistence where the existing transaction can safely continue; otherwise use existing transaction failure behavior. No job survives a rolled-back Tutor decision.
4. The primary terminal Tutor lifecycle does not await specialist generation. This is asynchronous work **after primary commit**, not fully parallel execution from the start of the primary call. The Worker may finish before or after the browser receives the terminal Tutor event; neither order authorizes a false visible-Canvas claim. Durable pending status, not an empty fake Scene, may appear through existing Studio delivery.
5. Reuse `JobHandlerRegistry` and `run_once` to claim in a short committed transaction. A proposed domain handler verifies current run/lease/order, reads and freezes the minimal capability pack (B1), records RUNNING/attempt admission, then commits/closes all database transactions before calling the Gateway. No database locks or transactions span model generation. The Gateway uses a separate fresh session whose execution-ledger write is completed after generation; do not copy a handler that holds domain locks across inference.
6. Separately validate the complete specialist result/schema, then application content, source/rights, Safety/Parent Boundary and domain checks. In a short acceptance transaction, recheck current permission, run/lease/deadline, source Tutor lineage and causal compatibility. Atomically accept the immutable private content version, Student-owned Scene/seed, required lifecycle Events/Snapshot and completed run link through existing authorities. A failure rolls back this entire acceptance unit, leaving no partial replacement. Library rendering is not validation authority.
7. Deliver committed pending/running/accepted/failure disposition through the existing authenticated resumable Studio feed and snapshot/reload path; any additive status payload must be versioned there, not a new feed. Render only committed accepted state. Keep usable committed Chat and permitted prior Scene on specialist failure. Recheck asset access on serving and show a safe permitted static/text equivalent when an asset fails.
8. Expose actual pinned content meaning and object handles through existing Studio context and unseen Events. Composition completion creates no automatic Tutor call, fake Student message or observation-watermark advance. Only the existing successful Tutor observation lifecycle marks content observed. A later object-explanation request uses Runtime-03. Future automatic post-render narration would be separately bounded behavior with an explicit additional call/latency cost; it is not V1.

**Primary/Canvas semantic alignment:** the specialist fulfils the ordered instructional objective, terminology, facts/values and constraints; it cannot invent an independent lesson or assessment. The primary Tutor must speak in shared instructional terms before acceptance, not unobserved layout details such as “the blue arrow on the left”, and must not claim the Canvas is visible before commit. Captions/labels/text alternatives belong to scene content; a competing Tutor dialogue or model-invented grading rule does not.

| Failure/choice | Applicable behavior |
|---|---|
| Explicit null order in a valid complete primary result | Normal Chat; no new visual mutation/composition |
| Usable validated primary result, but order/control semantically inadmissible | Reject only the optional visual request; no job or partial Scene replacement |
| Missing/invalid required primary field, incomplete response, provider failure or primary Safety refusal | Existing applicable Tutor failure/refusal/redirect behavior; no dispatch and no guaranteed recovered Chat |
| Specialist malformed/incomplete output, refusal, content rejection or provider failure | Fail/reject the run independently; committed usable Chat remains; no repair-model loop or false Scene success |
| Asset denial/failure | Permitted semantic/static/text fallback only; never reveal denied details |
| Timeout/cancellation/supersession | No accepted late result; preserve newer state and publish safe terminal disposition |

**Logical job, attempts and durable effects:** use an application-derived idempotency key from accepted source/order identity and exact capability version; duplicate admission resolves the same Job/run. The existing Job repository defaults to three attempts, so this path must explicitly propose `max_attempts=1` for inference and disable adapter/SDK automatic generation retries/fallback for its route. Normal composition has one additional call and no automatic semantic repair. A future retry policy would require explicit bounded approval and attempt/cost logging; it must not be inherited accidentally. One logical job does not guarantee exactly-once external inference: network ambiguity or a crash can leave an unknown provider outcome. Record that uncertainty rather than claiming zero cost or resending invisibly.

On crash before acceptance, existing lease expiry closes/exhausts the one-attempt Job; reconcile the dormant run to a safe terminal failure without another inference. If accepted effects committed but queue completion crashed, reconciliation reads the accepted run/effect identity, retains that successful Scene and settles queue metadata without regenerating or accepting again. The existing `run_once` settles the Job after its handler returns, so this crash window needs an explicit bounded domain reconciliation/settlement path in the same Worker architecture. Reuse run fields where sufficient; exact idempotent admission/settlement guards remain implementation proposals. Uniqueness/locking and accepted-run checks enforce **at-most-once accepted durable effects**, not exactly-once external calls. No Redis/Celery or new orchestration framework.

Timeout uses an application-owned deadline shorter than the claim lease, with provider cancellation when supported; cancellation is best-effort for compute but definitive for acceptance. A cancelled/superseded/expired run cannot accept a late response. Store bounded safe errors rather than provider text/private payloads. Accepted-run state remains authoritative if queue completion reporting disagrees.

**Stale versus harmless changes:** capture ordered objective, source/capability/content versions, target Scene identity and relevant semantic input state. A changed objective, replaced/closed Scene, incompatible parameter/source change or existing causal supersession rejects late composition; do not resurrect it. A record-only selection/highlight or other declared irrelevant event is not automatically a changed objective. Before accepting against a newer Scene version, a bounded application-owned compatibility check must prove changed fields are outside the order's semantic read set and preserve all newer Events/state; append with the freshly locked current version. If this cannot be proved, reject rather than silently overwrite/rebase. This proposed acceptance adapter does not weaken existing Runtime-03 cancellation/supersession or stale command admission globally.

A source/annotation routing decision still does not establish that its renderer exists. Known-content failure never silently invokes a specialist without an admitted COMPOSE order.

## B. Four-pattern contract and integration

### B1. Proposed bounded output contracts

Keep WorkspaceIntent v1 meanings and historical Tutor contracts intact. Proposed Tutor output v10 adds required-nullable `workspace_visual_order: null | TutorVisualOrderV1`, with version `tutor-visual-order-v1`. This replaces the earlier unimplemented primary `workspace_scene_proposal`/CREATE recommendation; V1 does not carry two competing scene-generation mechanisms. Exact names, schema version increment and storage/API details remain proposals, not deployed contracts. Both interfaces reject unknown fields and require provider/runtime parity fixtures.

| Interface/variant | Bounded model output | Application authority |
|---|---|---|
| Primary `REUSE` | Supplied opaque candidate handle/version and compact objective compatibility assertion | Resolve only semantically supplied pre-call content; recheck permission, objective/parameters/source/version/mode; zero composition calls |
| Primary `UPDATE` | Supplied current-context handle and 1–6 allowlisted semantic operations over existing handles | Derive actual Scene/base version and causal lineage from captured context; validate current state and actor/action contract; zero specialist calls |
| Primary `COMPOSE` | Compact educational order only: objective, relevant concept/fact/value/terminology items, locale, allowed pattern/mode, supplied source/asset handles, requested interaction and explicit instructional constraints; optional minimal task-specific presentation preference | Derive owner/session/source turn, execution identity, exact capability versions, policy, deadline and idempotency identity. | Specialist `SceneProposalV1` | `version: scene-proposal-v1`, typed pattern body, scene labels/captions, text equivalent, supplied source/asset/semantic-motion handles and declared instructional parameter data within the ordered bounds | Validate against server-pinned order/pack and accept once through Studio. Assign content/Scene IDs, contracts, permissions/review state and persisted lineage; specialist never writes or chooses those authorities |

Proposed primary COMPOSE limit: one pattern, objective ≤500 characters, at most 12 short instructional fact/value/term items, six constraints, six source and two asset handles, and ≤2 KiB final UTF-8 order. These convey meaning, not a hidden full scene: no object graph, complete label/layout inventory, drawing coordinates, executable formulas or grading rules. The specialist elaborates semantic objects/relations only within the fixed objective. If an essential fact cannot fit, simplify or clarify through Chat rather than silently omitting it. `quantity_visual` remains the canonical quantity/fraction family; the fraction mode is not a fifth renderer.

Retain proposed scene-body bounds: up to 12 objects, 20 relations, six source refs, two asset handles; labels ≤120 characters, explanations ≤300, text equivalent ≤1,200 and canonical body ≤8 KiB UTF-8. Locally unique opaque object IDs ≤64 characters do not encode answers. EXPLAIN/EXPLORE/GUIDED can only be used when the exact advertised contract enables that mode. The specialist cannot grant graded mode or invent validator rules. Pattern bodies B3–B6 and their domain limits remain unchanged.

The explicit runtime capability pack contains only the relevant pinned pattern/body schemas, permitted assets/anchors, approved visual examples and motion handles, required source excerpts/instructional facts, relevant current Scene meaning, output limits and domain constraints. Build it through existing application context/Gateway boundaries. No full Personal Memory, learner intelligence, raw history or private identifiers by default; a minimal presentation preference may be passed without its underlying history. Server-only lineage stays outside provider content. Pack assembly must fit a measured bounded request budget; it does not borrow capacity by truncating protected primary input. No whole-library prompt or extra semantic classifier/embedding pipeline.

Required primary schema failure follows primary Tutor behavior (A2); a schema-valid but semantically invalid order is rejected without composition. Required specialist schema failure rejects its run, not already committed usable Chat. Separate schema validity from factual entailment, permissions, Safety and content admission. A source ref proves neither truth nor rights. Runtime applies current effective policy independently to specialist labels/captions/text alternatives before display; rendering/layout/easing/exact calculations remain application-owned. Neither model supplies authoritative permission fields, Student/execution IDs, raw SVG/HTML/JS, remote fetches, callbacks, unrestricted paths, formulas-as-code or database writes.

Persisted seed/snapshot expansion still fits existing 16,384-byte budgets; Events fit 8,192 bytes and current interaction payloads 4,096 bytes. Check final serialized envelopes and UTF-8, not just object counts. Do not raise global limits for verbose output. A complete primary order cannot trigger execution until committed; all provider/runtime parsers must enforce the required-nullable sibling and historical v9 compatibility without silently accepting missing fields.

COMPOSE requires a compatible educational need (normally OPEN_ACTIVITY with VISUAL/INTERACTIVE for a registered pattern); substantial replacement may follow UPDATE_ACTIVITY but must resolve to a new content version/Scene with captured causal checks. Simple UPDATE retains `SET_HIGHLIGHT`, `SET_REVEALED` and registered `SET_PARAMETER` within the accepted Scene. Source/objective/whole/structural changes are not hidden parameter edits. No change/null does not admit a composition order. Broad REQUEST_CUSTOM_COMPOSE preserves its distinct bounded meaning.

No automatic primary CREATE fallback is proposed if the specialist fails. The same approved Worker/Gateway path handles new content and substantial recomposition; application code always owns acceptance.

### B2. Shared interaction and validation semantics

These are proposed registered action names, not claims that they exist now. Simple controls and object-specific Runtime-03 explanation do not invoke the composition specialist; a separate admitted COMPOSE order is required for generation. Each registration supplies an exact event kind/payload version, payload validator, reducer, actor restriction and interaction policy using existing `ActivityActionContract` machinery. Use a `visual-explanation-v1` event/payload namespace; retain Core lifecycle `studio.scene.accepted`, `studio.scene.activated`, and `studio.scene.status_changed`.

| Semantic action | Event/state effect and Tutor semantics |
|---|---|
| `SELECT_OBJECT`, `REVEAL_OBJECT`, `SET_HIGHLIGHT` | Record bounded object IDs/reveal/highlight state; `RECORD_ONLY`. Keyboard focus, hover and raw pointer coordinates are transient and not learning events |
| `MOVE_CONSTRAINED_POINT`, `SET_QUANTITY`, `SELECT_RELATION`, `ASSIGN_LABEL` | Only when exact pattern/mode advertises it. Commit semantic end state after structural/domain checks; `RECORD_ONLY`, not per-frame events. Label assignment selects supplied opaque labels; no free text |
| `REQUEST_EXPLANATION` | Selected object/relation IDs and current configuration only; `TUTOR_TRIGGERING`, one existing Runtime-03 continuation. No deterministic correctness verdict is implied |
| `SUBMIT_CONFIGURATION` | `TUTOR_TRIGGERING` only for an enabled guided activity with a versioned server validator; preserve submitted configuration and its result separately from later exploration |
| Tutor-originated UPDATE | Application maps validated operations to registered Tutor-only events. `RECORD_ONLY`; must not create a StudentInteraction, count as Student performance or recursively call Tutor |

For non-graded exploration, `SemanticValidationPolicy.NONE` means no academic answer grading for that action. Payload, safety, ownership, content admission, permitted parameter ranges and geometric/quantity invariants still apply. Guided/graded modes require `SemanticValidationPolicy.REQUIRED` and exact server validator key/version. Reuse existing `VALID`, `INVALID`, `UNDER_SPECIFIED`, `VALID_ALTERNATIVE`, `INCOMPLETE`; never reinterpret `VALID` as scientific certification or mastery. Help/explanation may reach the Tutor without an answer key; a correctness badge may not.

Cross-actor restrictions for the new actions require explicit enforcement at admission: a Student cannot submit a Tutor-only highlight/update command by changing an actor field. Record-only events remain observable under the existing watermark; Tutor-triggering events preserve current exclusive claim, cancellation, causal ordering and immutable submitted-state lineage. Rejected operations do not become accepted Events. No direct Candidate, Evidence, Personal Facts or intelligence writes.

For review, proposed durable event kinds map one-to-one to these actions: `visual.object.selected`, `visual.object.revealed`, `visual.highlight.set`, `visual.point.moved`, `visual.quantity.set`, `visual.relation.selected`, `visual.label.assigned`, `visual.explanation.requested`, and `visual.configuration.submitted`. Tutor `SET_PARAMETER` maps to `visual.parameter.set`; Tutor reveal/highlight use the same semantic kinds with server-assigned Tutor actor. Every registration pins `visual-explanation-v1` event schema plus its exact action-payload schema. These names extend subject action registrations; they do not add a new feed or change Core event sequencing.

### B3. `process_cycle` — process and relationship explanation

- **Purpose:** Explain a finite process, recurrence or supported branching relationship. Unsuitable for unrestricted concept maps, continuous physical simulation or implying a single order where the source supports alternatives/parallel paths.
- **Semantic body:** 2–12 labeled stages/entities, up to 20 typed directed relations (`precedes`, `transforms_to`, `returns_to`, `branches_to`), optional branch condition/caption and source handles per relation. Topology declares `sequence`, `cycle`, or `branched`; it controls layout without fabricating links. A cycle requires an explicit supported return relation. Do not close an arrow because the pattern is named process_cycle.
- **First-slice modes/actions:** Bounded EXPLAIN sequences and cycles, including an explicit source-supported return relation, are in slice 1. Selecting an object, highlighting/de-emphasizing, revealing it, and requesting an object-specific Tutor explanation are explanatory controls; selection/highlight/reveal are record-only and an explicit explanation request triggers Runtime-03. Advertise only these exact supported actions; their presence does not enable graded ordering or graph editing. The renderer contract must accurately advertise its control support even though the instructional mode is EXPLAIN.
- **Later modes/actions:** Multi-branch/merge, conditional/parallel paths and arbitrary graph topology remain later process work; they are not required for the first sequence/cycle slice. Node creation/deletion, rewiring and unrestricted graph editing remain outside bounded V1 and need separate demonstrated need/approval. Guided order/relation grading waits for slice 4 and a source-reviewed server rule with allowed alternatives. The accepted sand/water filtration ordering activity remains its existing precise activity; it is not the new first-slice deliverable.
- **Checks/limits:** Unique IDs, resolvable endpoints, no duplicate edges or undeclared self-loops; declared topology consistency and bounded captions. A graph check cannot establish causality, timing, conservation or scientific truth. Each instructional claim/arrow must be supported by the selected source or explicitly identified as a model-knowledge draft. Never grade from a model-invented answer key.
- **Fallback:** Ordered or grouped text lists with explicit named relationships, branch conditions and return explanation; keyboard list selections equal pointer selections. Narrow layout may use stacked stages plus relationship text without changing topology.
- **Reusable examples:** Water movement between surface, atmosphere and ground (include only grounded paths, not a forced ring); a sourced butterfly life cycle; source-supported filtration steps; language writing/revision (`plan → draft → review`, with revision returning to draft only when taught). The language example uses the same body/parser/view and ENGLISH or ARABIC subject registration, not Science attribution because arrows exist. These are design cases, not newly verified instructional sources or prepared lessons proving generation.

### B4. `labeled_diagram` — parts and relationships

- **Purpose:** Identify parts, positions and function in a coherent whole. Unsuitable when numerical geometry must be exact, a photo is ambiguous, or a label would pretend to identify an uncertain biological structure.
- **Semantic body:** One application-owned schematic type or authorized referenced image; up to 12 parts/labels with normalized anchor regions, optional `part_of`/`connected_to` relations, reveal group, and source handle. No arbitrary drawing markup. Image-relative anchors refer to a specific immutable image version and aspect ratio; reject out-of-bounds regions. Schematic types are bounded rendering shapes, not lesson IDs.
- **Modes/actions:** EXPLAIN shows/reveals labels; EXPLORE selects a part and requests an explanation. GUIDED permits assignment of supplied labels to defined parts followed by submission against a server-reviewed answer mapping, including declared alternatives. Labels that reveal the answer must not masquerade as an independent assessment.
- **Checks/limits:** Existing part references, bounded geometry, complete text equivalent; source/asset match, meaningful labeling and visibility review. Normalized coordinates alone do not prove that an arrow points to the correct part. A generated image cannot supply anatomical truth. If useful illustration is unavailable, use an honest text explanation rather than a confusing collection of boxes.
- **Fallback/examples:** Accessible part-name/function list and label-assignment controls. A plant's parts, a simple circuit's components, and subject/verb/object spans in a short English or Arabic sentence use the same labeling pattern. Language spans reference grapheme-safe text ranges/opaque tokens in the immutable content, retain diacritics, and do not add a general grammar grader or replace accepted sentence-ordering activities.

### B5. `geometry_scene` — explanation versus constrained manipulation

- **Purpose:** Explain geometric relationships, measurements and invariants. Distinguish a labeled illustrative drawing from a mathematically constrained construction. Unsuitable for arbitrary theorem proving, unrestricted construction tools, 3D, or treating a sketch/pixel distance as a measurement.
- **Semantic body:** Up to 12 points, segments, circles, polygons and angle markers counted within the shared object cap. Exact scalar data uses bounded rational pairs; relations are allowlisted `incident`, `parallel`, `perpendicular`, `equal_length`, `fixed_distance`. Each constrained point has a declared domain and application-owned construction rule. No expressions, scripts or JessieCode from the model.
- **EXPLAIN:** Application lays out a labeled shape. An illustrative not-to-scale view states this; exact values/claims must agree or be omitted. Highlight side/angle/height without reconstructing the Scene.
- **EXPLORE/GUIDED:** Move only enabled points using pointer or coordinate/step controls. The renderer projects motion onto the allowed domain; the server recomputes and validates the submitted canonical configuration with a declared tolerance/rounding policy owned by the exact domain contract. GUIDED submission requires an application-owned criterion, never a browser/library assertion of correctness.
- **Stress case:** Drag the top of a triangle along a line parallel to its fixed base; the application maintains a fixed perpendicular height and computes area from the accepted base/height. This is different from explaining labeled triangle parts. Degenerate/self-intersecting constructions, incompatible constraints or out-of-domain moves are rejected without changing accepted state. Exact rational invariants use exact arithmetic; approximate constructions must explicitly declare numeric limits and tolerance before promotion.
- **Fallback/examples:** List points, relationships and measurements with equivalent keyboard controls; a rectangle's perimeter, triangle base/height/area, and circle radius/diameter use the same geometry view with different semantic bodies. A visual triangle-angle sum is not proof of a general theorem. Dynamic geometry library output is never server validation authority.

### B6. `fraction_model / quantity_visual` — explicit wholes and values

- **Purpose:** Show quantities, equal parts, equivalence and comparisons. Unsuitable for fraction algorithms, decimal operations, measurement accuracy, division strategy or ratio claims beyond the enabled mode. Approved family direction does not authorize full fraction arithmetic.
- **Semantic body:** Canonical pattern `quantity_visual`, `representation` of `equal_parts_bar`, `equal_parts_area`, or `discrete_set`; stable whole IDs, unit, exact rational whole value, equal partition count, selected part IDs and optional explicit mapping between equivalent representations. Proposed initial denominator cap 12 and total visible parts/items 24 (body's semantic object cap counts whole/model objects, not repeated generated partition marks). No floating-point source truth.
- **Modes/actions:** EXPLAIN shows unit fraction/simple equivalence; EXPLORE changes the number of selected parts or an allowed partition parameter and highlights equivalence. `SET_QUANTITY` is record-only; GUIDED submission needs exact server arithmetic and whole/partition validation. No arbitrary field entry or model-authored grading rule.
- **Invariants:** Whole identity and unit remain explicit; denominator positive; each partition is equal measure within its whole; selected membership unique and within range; selected value = whole value × selected count / partition count. Equivalent forms require equal total value and compatible whole/unit, not equal shaded area on differently scaled pictures. Improper fractions need explicitly multiple equal wholes; exclude them from the initial simple-fraction mode. Changing a denominator cannot silently preserve an incompatible selection or change the whole; revalidate the entire state.
- **Fallback/examples:** Text such as “3 of 4 equal parts of one whole; value 3/4”, with increment/decrement controls. Three quarters of a strip, half of a declared set of 8 counters, and two fourths compared with one half reuse the same family. A Science quantity example may show parts of an explicitly defined sample; do not infer a measurement from the picture.
- **Non-duplication:** Keep accepted Make-Ten transfer, decimal number-line comparison/rounding, and exact hundredths place-value ADD/SUBTRACT on their existing contracts. Route compatible precise tasks there. Fraction operations, fraction number-line modes and division retain the corrected renderer planning scope and separate promotion; this family does not claim their coverage.

## C. Generation, persistence, reuse, and privacy

### C1. Three identities and smallest storage extension

| Entity | Authority and lifetime |
|---|---|
| Pattern/template | Application-owned versioned schema, view/layout policy, actions and validators registered through Subject Capability. Reusable without containing any Student information; no new template platform |

| Student Scene instance + Events/Snapshot | Existing `StudioScene` with its seed, exact contracts, source Tutor lineage and Student/session ownership; Events preserve interaction history, Snapshot is rebuildable. Existing `status = ACCEPTED` means accepted into Studio state, not academically reviewed or Product Owner accepted |

Current `StudioScene` is explicitly Student/session-bound; `ContentDocument` ingestion accepts PDF/Markdown originals and deduplicates per Student checksum. Neither is a global reusable scene library. Do not overload a Student Scene as shared content or a generated description as an original book.

Propose one immutable PostgreSQL relation, provisionally `StudioInstructionalContentVersion`, inside existing Studio persistence: content ID/version, pattern/contract version, typed body JSONB/hash, objective and parameter signature, subject/concepts, locale/direction, supported level range, source refs/revisions, asset manifest, scope/owner, rights/review metadata and creation lineage. Default scope `STUDENT_PRIVATE` with owner required; only authorized project-reviewed records may have `PROJECT_SHARED`. Rights scope is the intersection of all sources/assets, never broader than an underlying source. An immutable superseding record carries review/rights changes; revoked items are excluded from new selection.

This additive relation is proposed because content needs independent immutable identity, permissions and indexed selection without copying attempts. It is not another scene store: no Student answers, mutable positions, Event log or Snapshot belongs there. Use existing PostgreSQL transactions/indexes, not vector infrastructure or a new service. Store a pinned content reference/hash and full safe semantic seed in existing Scene JSONB, avoiding a required new Scene column in the first slice. Validate references in the activation transaction. Keep protected server grading criteria out of browser seed/feed payloads; a content variant with assessment uses a private versioned validator policy reference.

Generated content may inadvertently echo Personal Memory or Student details even when prompted otherwise. Therefore every new model-generated record starts Student-private and unreviewed, independent of whether it looks generic. There is no automatic cross-Student promotion or automated “anonymization” promise. A shared version must be separately authored/reviewed from instructional sources, with positive checks that it contains no names, Personal Facts, answers, original Student work or interaction logs. A saved Scene never becomes a shared record by copying it.

Use ordinary permission/metadata queries in the existing application database. Historical seed, renderer/reducer versions and Events remain pinned. Template updates affect future instances only. Exact unavailable historical contracts must give an honest accessible fallback, not silently use the newest renderer. Preserve immutable bytes for reproducibility while enforcing current access/revocation restrictions: historical reproducibility does not permit serving a revoked asset. Show retained semantic text where permitted and a clear unavailable-media state.

### C3. Content admission and factual authority

Separate `STRUCTURE_CHECKED`, `SOURCE_LINKED`, and `REVIEWED` concepts; never collapse them into “correct”. Unreviewed content never becomes a graded answer authority or shared reviewed item. Admission applies the existing effective Safety/Parent Boundary decision to all visible labels, captions, equivalent text and media, including reused content; reuse cannot bypass changed policy. Runtime implementation must suppress restricted visual output together with the restricted Tutor answer. Prompt-only safety is insufficient.

Generated and reused visual text enters normal Tutor/interaction history only through existing boundaries. Selecting, displaying, liking or repeating a Scene is not proof of learning. ## D. Visual quality, correctness, and focused library comparison

### D1. Visual acceptance contract
