**Principle:** deterministic subject validation checks bounded mathematical state. It does not become a generic tutor, select pedagogy, decide safety, invent source facts, or over-constrain a legitimate alternative method. `Reference-grounded` means a later source/context check may be needed for a word-problem interpretation; it is not a reason to invent an LLM validator call.

## Decimal operation contract — LINA DESIGN RECOMMENDATION

`decimal_operation_validator` serves node 36 through `place_value_workspace`, alongside the existing place-value validator. Inputs: immutable nonnegative operands, ADD/SUBTRACT, common hundredths scale, typed unit counts by place, exchange history, working result, submitted equation and exact Scene revision. First subtraction tasks use minuend ≥ subtrahend. A quantity is the sum of count × place weight in integer hundredths. Exchange one unit for ten next-smaller units (or reverse) without changing that sum; then combine/remove only the selected operand quantity. Validate alignment by unit identity, nonnegative available counts, no duplicated/lost quantity, and exact result = a + b or a − b. Accept equivalent regrouping paths and zero padding; 1.2 and 1.20 denote the same amount. A numerically correct answer with an inconsistent submitted model is not a valid configuration. Bounds reject unsupported precision rather than silently rounding; alternative written reasoning belongs to Tutor. This is a planning contract, not implemented validation.

Expression node 1 has separate evaluation and writing/interpretation requirements. Bounded trees can check operation relationships; arbitrary language meaning cannot be established by evaluating to the same number. Its coverage remains partial. A fraction or line-plot validator checks exact rational arithmetic in an authored mathematical task; an ambiguous contextual problem stays reference-grounded. Source facts and limits are traced in [10_CORRECTION_RECORD.md](10_CORRECTION_RECORD.md).

## Validator contract recommendations

- Return a **typed status** such as `VALID`, `INVALID`, or `UNDER_SPECIFIED`, with safe feedback codes and valid next actions—not an unbounded natural-language lesson.
- Preserve the submitted state and causal renderer revision so Tutor can understand a meaningful attempt later. Raw Student work/original image remains separate source authority.
- Version validators and fixtures with their capability; a changed validator must be testable against prior valid and invalid states.
- For visual input, define tolerance in mathematical units (for example, grid increment), never opaque screen pixels.
- A subject validator is invoked through the accepted Subject Capability boundary when a renderer task is promoted. Studio Core sees only result status and generic lifecycle semantics.
