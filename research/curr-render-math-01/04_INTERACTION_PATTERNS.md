# CURR-RENDER-MATH-01 — Semantic Interaction Patterns

**Boundary:** These are learning-action archetypes, not browser event names. The accepted Studio Core records bounded semantic Events through exact Activity/Renderer contracts. Each Activity declares RECORD_ONLY versus Tutor-triggering actions; a planning label cannot override that declaration. It must not infer learning evidence from a click, drag, or completed animation alone.

| Pattern | Purpose and Grade 5 examples | Semantic meaning | Record-only vs Tutor-triggering | Keyboard / touch / accessibility | Validation and recovery |
|---|---|---|---|---|---|
| `select` | choose an interval, shape property, fraction model, or answer option | learner selects an offered mathematical object | record-only while exploring; trigger only on committed answer or Tutor-requested check | Tab/arrow/Space; tap; selected state announced | selected ID must be allowlisted; clear selection and explain available choices |
| `transfer` | move a digit across place values; transfer a fraction share | learner assigns a typed item to a typed target | record-only until commit; trigger when a Tutor-requested representation is completed | buttons “move left/right” and list targets; drag optional | validator rejects invalid target with specific state feedback; undo preserves prior state |
| `partition` | split a bar, area, or prism into equal units/layers | learner defines mathematical structure | trigger on submitted partition where it reveals reasoning | keyboard stepper/number entry; tap controls | enforce equal, finite partitions and declared whole; revert to last valid partition |
| `group` | make equal groups for sharing/division or arrays | learner establishes grouping relation | trigger on completed grouping if task goal is grouping | select then “group”; tap-to-add; non-color labels | validate each item membership/no duplicate; surface remaining items |
| `reorder` | order decimals/fractions or arrange expression tokens | learner asserts an ordering/structure | trigger on submit, not each move | keyboard move earlier/later; touch drag with buttons | compare semantic order; allow ties/equivalent forms when task permits |
| `label` | label axes, dimensions, place values, properties | learner assigns a concept label | trigger only when task requires explanation or label check | text input with available terms; touch keyboard | canonical term/value validation; preserve attempted label and offer correction |
| `plot` | place point or line-plot observation | learner maps a value to a coordinate/scale | trigger on a committed point/set | coordinate entry and arrow nudge; tap/click | snap to valid increment/tolerance; show exact committed coordinate |
| `construct` | create a prism layer, array partition, or shape classification set | learner builds a bounded mathematical object | trigger on “check construction” or an observable solution state | steppers/buttons plus optional direct manipulation | validate structural invariants; undo/redo and reset to seeded state |
| `enter_value` | partial product, quotient digit, converted measure, coordinate | learner provides a scalar mathematical value | trigger on submit or Tutor-requested check | native numeric/text entry with locale-aware explanation | parse bounded numeric grammar, range/unit checks; retain invalid entry with clear error |
| `enter_expression` | write an equivalent expression or numerical rule | learner provides structured notation | trigger on explicit submission | keyboard-first; MathLive only if later proved necessary | parser/equivalence validator; do not reject a mathematically equivalent syntax merely because it differs from one key |
| `submit_step` | submit a division subtraction, fraction operation, or formula stage | learner asks to validate an intermediate state | normally Tutor-triggering `StudentInteraction` because it can change support | Enter/primary button; touch target | partial-state validator returns valid / invalid / under-specified plus next permissible action, never an ungrounded Tutor verdict |
| `submit_configuration` | submit a completed graph, model, conversion table, or classification | learner presents a complete bounded solution state | Tutor-triggering when requested or pedagogically meaningful | primary button; review summary before submit | complete-state validator; immutable committed snapshot; allow edit/retry |
| `reveal_hide` | reveal a hint, worked layer, label, or answer after a choice | learner requests support or controls cognitive load | record-only by default; hint request may be Tutor-relevant | keyboard toggle; touch toggle; state announced | no correctness claim; preserve reveal level as interaction context, not evidence |
| `compare` | state greater/less/equivalent or larger/smaller after scaling | learner asserts a relation | trigger on commit | three labelled buttons / keyboard | exact relation validator; give model-linked explanation after feedback |
| `annotate` | later mark original homework or renderer view with arrow/highlight/note | learner adds a source-linked observation | record-only unless explicitly submitted as explanation | keyboard note and selectable anchor; touch drawing is additive | annotation geometry/text bounded and source-linked; never overwrite original |
| `manipulate_parameter` | adjust scale, denominator, dimensions, or point values to observe a relationship | learner explores a constrained parameter | record-only while exploring; trigger on a submitted prediction/explanation | slider plus numeric input and buttons; touch slider | min/max/step and dependency validation; reset to authored configuration |

## Event policy guidance

1. The durable envelope should identify actor, renderer/activity type, source turn, scene version, monotonically ordered action, idempotency key, and typed payload. It should not contain raw pointer coordinates as semantic truth.
2. `SUBMIT_STEP`, `SUBMIT_CONFIGURATION`, and an explicit explanation/answer are the strongest candidates for future Tutor-visible StudentInteraction. Exploration events normally remain context only.
3. A valid action is not automatically `independent_success`; a Tutor-selected strategy is not effectiveness evidence. Existing Session/Segment authority remains unchanged.
4. Cancellation, stale scene, failed validation, and renderer error must be first-class recoverable outcomes—not hidden client state.

## Interaction-language boundary

Academic subject is Math. The interaction language can be Arabic, English, or mixed without changing the Math capability. Arabic prose uses `dir=auto`; numerals, coordinates, fraction notation, and expressions retain stable mathematical LTR conventions. Every visual action must be usable by keyboard and touch; dragging is optional enhancement, never the only path.

## Correction-specific operations — proposed, not runtime contract changes

- Decimal addition/subtraction: `exchange_units` conserves an operand's scaled value (one unit equals ten of the next smaller place); `combine` or `remove` changes the working result according to the selected operation. Keep source operands immutable; distinguish equivalent regrouping from moving a digit to change its value. Zero placeholders and different valid exchange sequences are allowed. Submit both result and model state; replay the same exact arithmetic server-side.
- Expressions: evaluation mode validates grouping and computed value; writing mode assembles an allowlisted operation tree for an authored calculation; interpretation mode selects a bounded structural relationship without requiring calculation. Equal numerical results alone are insufficient for the latter two modes. Free-form Student explanations remain Chat-owned; no unrestricted Canvas text is introduced.
- Division: group allocation, area partition and quotient-chunk entry are distinct mode operations. Decimal scale changes preserve the ratio by changing both operands together. A bring-down action belongs only to the algorithm mode. First-slice partial-quotient exploration is RECORD_ONLY; its explicit submitted configuration alone requests a Tutor continuation, subject to the eventual exact Activity contract.
- Measurement conversion: typed source/target units and an entered equivalent value; line plots: observation-ID placement/removal and an explicitly submitted aggregate. Never treat converting a unit as moving a data observation.
- Make-Ten remains the accepted cross-grade `TRANSFER_ITEM` contract. These planning archetypes do not rename it or any persisted Event.

All first-slice controls are bounded and accessible. Browser feedback is provisional; correctness, exact versions, durable Events/Snapshot and submission identity remain server-owned. There is one Student-facing Tutor and no direct Canvas Evidence, intelligence, or Personal Facts write.
