# STUDIO-ORCH-01 — Product Owner Decision Packet

**Status:** Decision packet only. Approval is required before any finding is
promoted into governing architecture, tasks, or implementation.

## Decision 1 — Target Studio architecture

**Question:** Should Lina adopt the subject-agnostic Studio Core with
application-owned event log plus snapshot, one Student-facing Tutor, deterministic
renderers for routine work, and an optional constrained Canvas specialist?

**Recommended answer:** Yes.

**Why:** It provides complete Tutor visibility of meaningful Canvas work while
preserving routine Tutor latency and preventing Canvas or a framework from
becoming a second Tutor or state authority.

**Alternative:** Introduce a Teaching Manager above Tutor/Canvas specialists.

**Impact:** Establishes the architecture target for future tasks; does not
authorize code or dependencies.

**Risk:** Without this direction, FE-02 can only remain a presentation shell or
drift into unowned browser state.

**Confidence:** High.
## Decision 2 — Proof A foundation

**Question:** Approve make-ten 9 + 6 as the first bidirectional Studio proof?

**Recommended answer:** Yes; use deterministic React/SVG with one committed
counter-transfer operation.

**Why:** It is simple enough to prove state history, watermark correctness,
idempotency, stale rejection, accessibility, language direction, and Tutor
continuation without a specialist.

**Alternative:** Start with fractions or geometry.

**Impact:** Gives the implementation a narrow measurable first artifact and
avoids combining protocol proof with specialist quality proof.

**Risk:** A broader first case makes failure attribution difficult.

**Confidence:** High.

## Decision 3 — Release-1 persistence and transport boundary

**Question:** Approve event log plus materialized snapshot as Studio state, with
existing Tutor SSE retained and a dedicated resumable Studio feed introduced
after/through the proof?

**Recommended answer:** Yes.

**Why:** Snapshot-only cannot reconstruct learning action history; Tutor SSE
should retain terminal Tutor authority rather than carry concurrent Canvas
lifecycle.

**Alternative:** Terminal envelope plus snapshot polling for every release.

**Impact:** Requires a bounded new state/protocol capability before FE-02 can
become the real Studio.

**Risk:** Polling-only or message-payload state will not reliably support
Canvas-first, parallel, and interleaved work.

**Confidence:** High.

## Decision 4 — Specialist eligibility envelope

**Question:** Approve an optional Canvas specialist only when application rule
plus Tutor request confirms an allowed subject capability, safe renderer/validator,
a real deterministic-renderer gap, and no blocked learning flow?

**Recommended answer:** Yes; run it application-scheduled and parallel/deferred,
never as a routine blocking call.

**Why:** It preserves immediate Tutor guidance and makes specialist cost/quality
measurable.

**Alternative:** Run a Canvas model on every visually oriented turn.

**Impact:** Proof B may use at most one additional Canvas call on eligible turns.

**Risk:** Always-on calls increase latency, cost, privacy surface, and second
Tutor risk.

**Confidence:** Medium-high.

## Decision 5 — Bounded reuse evaluation

**Question:** Approve a later package/protocol evaluation after Proof A for a
small Lina Scene spec versus A2UI, AG-UI semantics, and OpenMAIC DSL/renderer
packages?

**Recommended answer:** Yes, as a comparison only; reject full platform/runtime
adoption unless evidence wins.

**Why:** A2UI/AG-UI/OpenMAIC offer useful current capabilities, but Lina must
retain state, safety, authorization, and transport authority.

**Alternative:** Adopt a framework now.

**Impact:** Produces an adopt/partial-adopt/reject record before dependency work.

**Risk:** Immediate adoption risks framework capture, broader product scope, and
unproven accessibility/security behavior.

**Confidence:** High.
